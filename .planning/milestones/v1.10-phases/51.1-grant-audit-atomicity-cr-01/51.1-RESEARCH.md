## Summary

CR-01 is narrow and mechanically well-understood: `record_github_grant` (`crates/brokerd/src/audit.rs:537-567`) issues an `INSERT OR IGNORE` into `session_grants` as its own autocommit statement, then — only when that insert was fresh — calls `append_event` as a **second**, independent autocommit transaction. Between those two statements there is no shared transaction boundary, so a crash or I/O fault inside `append_event` (which itself already **is** transactional, per the Phase-51 D1/D2 fix) leaves a durable, ungoverned `session_grants` row with no matching `github_grant_authorized` event in the hash chain. A retry's `INSERT OR IGNORE` then reports zero affected rows, silently skips the event, and returns `Ok(())` — `has_github_grant` (a bare `SELECT 1 FROM session_grants`) has no way to detect the missing event.

The fix is a small, already-sanctioned pattern: wrap the whole function body in **one** `rusqlite::Transaction::new_unchecked(conn, TransactionBehavior::Immediate)`, and call `append_event(&tx, ...)` instead of `append_event(conn, ...)`. `append_event` already contains the exact re-entrancy check this needs (`audit.rs:1065`, `if conn.is_autocommit() { open own tx } else { join enclosing tx }`), and SQLite's `is_autocommit()` state is native connection state — not a rusqlite-side flag — so it correctly reports `false` once `record_github_grant`'s own `Transaction::new_unchecked` has issued `BEGIN IMMEDIATE`. **This session independently compiled and ran a working prototype of exactly this fix** (created as a throwaway `crates/brokerd/tests/zz_research_scratch_cr01.rs`, executed, then deleted — `git status --porcelain` clean before and after) and confirmed: (a) `append_event(&tx, ...)` joins the enclosing transaction without nesting, (b) dropping the `events` table before calling the fixed function makes the append fail deterministically and rolls back the already-staged `session_grants` insert (0 rows survive), and (c) a subsequent retry after repairing the schema yields exactly one `session_grants` row and exactly one `github_grant_authorized` event.

`Transaction::new_unchecked` (not `Connection::transaction_with_behavior`) is required because `record_github_grant`'s public signature takes `conn: &rusqlite::Connection` (a shared reference) at every one of its 12+ call sites (`main.rs`, 4 in-crate unit tests, 2 `confirmation.rs` unit tests, `s38_github_pr.rs`, `audit_chain_fork_regression.rs`) — `transaction_with_behavior(&mut self, ...)` needs `&mut Connection`, which none of those callers currently hold, and changing the signature would ripple `mut` through every caller for no functional gain (the DESIGN doc already authorized exactly this shared-reference pattern for `append_event`'s own autocommit branch, so reusing it here is the minimal, precedent-following change).

**Primary recommendation:** wrap `record_github_grant`'s existing two statements in one `Transaction::new_unchecked(conn, TransactionBehavior::Immediate)`, call `append_event(&tx, key, &event, parent_hash.as_deref())` in place of `append_event(conn, ...)`, and `tx.commit()?` only at the very end. Add a new regression test file `crates/brokerd/tests/grant_audit_atomicity_regression.rs` that forces the append to fail by dropping the `events` table on the same connection immediately before calling `record_github_grant`, asserts the `session_grants` row did NOT survive and `has_github_grant` is false, repairs the schema via `conn.execute_batch(brokerd::audit::SCHEMA_DDL)` (idempotent `CREATE TABLE IF NOT EXISTS`), retries, and asserts exactly one grant row and exactly one `github_grant_authorized` event. `has_github_grant` itself needs **no code change** — once the insert and the event share one commit, the "row present, event absent" state becomes structurally unreachable, which is exactly what success criterion 3 requires.

### Pattern 1: Join-enclosing-transaction via `is_autocommit()` re-entrancy (the sanctioned choke-point pattern)
**What:** A function that must write two related rows atomically opens ONE `IMMEDIATE` transaction on its `&Connection`/`&mut Connection`, and any nested audit-append call detects the already-open transaction and appends into it rather than opening a second, nested one.
**When to use:** Any time `append_event` must commit together with a sibling write (a CAS row, a capability row, a checkpoint row).
**Where it's already used (mirror these, don't invent a new shape):**
- `confirmation.rs:1163,1179` (`confirm`, `email.send` arm) — `conn.transaction_with_behavior(Immediate)` (caller owns `&mut Connection`), then `append_event(&tx, ...)`, then `tx.commit()`.
- `server.rs:1184,1226` (`evaluate_plan_node_and_record`, `sent_plan_node`) — `locked.transaction_with_behavior(Immediate)` where `locked: MutexGuard<Connection>` (via `DerefMut`), then `append_event(&tx, ...)`, then `tx.commit()`.
- `server.rs:1557,1579` (`evaluate_plan_node_and_record`, github.pr CAS reservation) — **the closest structural analog to CR-01**: an `INSERT OR IGNORE`-style CAS (`reserve_created_pr`) followed by a conditional `append_event`, both inside one `locked.transaction_with_behavior(Immediate)`. `record_github_grant`'s own `INSERT OR IGNORE` + conditional `append_event` shape is IDENTICAL to this one — the only difference is `record_github_grant` currently lacks the enclosing transaction these three sites already have. `[VERIFIED: crates/brokerd/src/server.rs:1546-1588]` — read directly this session; quoted below.


**Why `record_github_grant` needs `Transaction::new_unchecked`, not `transaction_with_behavior`:** its signature is `pub fn record_github_grant(conn: &rusqlite::Connection, key: &[u8], session_id: &str) -> Result<()>` (`audit.rs:537-541`, read this session) — a **shared** reference, matching every one of its 12+ call sites (`main.rs:1255`, `audit.rs` unit tests, `confirmation.rs:3139,3226`, `s38_github_pr.rs:319`, `audit_chain_fork_regression.rs:68`). `Connection::transaction_with_behavior(&mut self, ...)` requires `&mut Connection` (`rusqlite-0.32.1/src/transaction.rs:428-433`, read this session) — unavailable here without rippling `mut` through every caller. `Transaction::new_unchecked(conn: &Connection, behavior)` (`rusqlite-0.32.1/src/transaction.rs:116-129`, read this session) takes exactly the shared reference `record_github_grant` already has, and is the identical mechanism `append_event`'s own autocommit branch already uses and that the DESIGN doc already authorized. `[VERIFIED: rusqlite 0.32.1 source, read directly this session]`

### Anti-Patterns to Avoid
- **Do not change `record_github_grant`'s public `&Connection` signature to `&mut Connection`.** Not required (see above) and increases diff size/blast radius for no benefit.
- **Do not add a second, independent `append_event` call site or a raw `INSERT INTO events`.** The DESIGN doc's Section 3 "choke point" invariant requires exactly one public append entry point; a parallel append path is explicitly rejected by the gate.
- **Do not touch `verify_chain`, `current_chain_head`, `compute_event_hash`, `verify_event_hash`, `compute_anchor_mac`, or `verify_anchor_mac`.** These six functions were byte-compared unchanged by Plan 51-07's Gate A and the independent adversarial trace; CR-01's fix must preserve that (success criterion 4).
- **Do not derive, assign, or reuse `read_event_id` as a causal `parent_id`, or vice versa.** `record_github_grant`'s grant event has no `read_event_id`/`provenance_chain` involvement today and must not gain one — the two graphs (causal chain vs. provenance/taint graph) must stay disjoint (DESIGN doc §2, `server.rs:941,957,973`).

## Detailed Research Answers

### Q1 — Nested-transaction semantics (VERIFIED empirically, not just by inspection)

`append_event`'s signature is `pub fn append_event(conn: &rusqlite::Connection, key: &[u8], event: &Event, parent_hash: Option<&str>) -> Result<String>` (`audit.rs:978-983`, read this session) — it takes `&rusqlite::Connection`, not `&Transaction` and not a generic. It decides whether to open its own transaction via `conn.is_autocommit()` (`audit.rs:1065`): if `true` (no transaction currently open on this connection handle), it opens its own `Transaction::new_unchecked(conn, TransactionBehavior::Immediate)`, runs the append, and commits; if `false` (a transaction is ALREADY open on this connection — e.g. the caller opened one), it calls `append_at_head(conn)` directly, joining the caller's transaction with **no** nested `BEGIN`.

`Connection::is_autocommit()` delegates straight to SQLite's native `sqlite3_get_autocommit()` C API state (`rusqlite-0.32.1/src/lib.rs:1043-1045`, read this session: `self.db.borrow().is_autocommit()`) — it is real SQLite connection state, not a rusqlite-side bookkeeping flag, so it correctly reflects whatever transaction is currently open on that connection handle regardless of how that transaction was opened (`Transaction::new`, `Transaction::new_unchecked`, or a raw `execute_batch("BEGIN ...")`).

`51-REVIEW.md`'s claim — "Because `append_event` detects the enclosing transaction, it will append at the locked durable head without opening a nested transaction" — is therefore **correct**, and this session independently proved it by compiling and running exactly this shape (see prototype in Summary above): `record_github_grant_fixed` opens `let tx = Transaction::new_unchecked(conn, Immediate)`, asserts `!tx.is_autocommit()` (passed), then calls `append_event(&tx, ...)` (passing `&tx`, which `Deref`s to `&Connection` — `rusqlite-0.32.1/src/transaction.rs:232-238`, read this session) — this ran green with no "cannot start a transaction within a transaction" error, confirming `append_event` correctly joins rather than nests.

`rusqlite::Transaction::new_unchecked` is used (not `conn.transaction_with_behavior`) purely because `record_github_grant` — like `append_event` itself — is locked to a shared `&rusqlite::Connection` parameter at all of its call sites, and `transaction_with_behavior(&mut self, ...)` requires `&mut Connection` (`rusqlite-0.32.1/src/transaction.rs:428-433`, read this session), which none of `record_github_grant`'s callers currently hold or need to hold for any other reason. This is not a borrow-checker workaround that weakens safety — `new_unchecked` still issues a real `BEGIN IMMEDIATE` and still relies on the same `is_autocommit()` re-entrancy discipline; it only trades a compile-time nested-transaction guarantee for a runtime one (a nested `BEGIN` on an already-open transaction would fail at the SQL level with a `rusqlite::Error`, which propagates as `Err` — fail-closed, not silently accepted). `[VERIFIED: crates/brokerd/src/audit.rs:978-1076, rusqlite-0.32.1/src/transaction.rs:98-129,232-238,416-433, rusqlite-0.32.1/src/lib.rs:1043-1045 — all read directly this session; mechanism additionally proven by a throwaway compiled-and-executed prototype, deleted after use]`

### Q3 — Deterministic fault injection (empirically verified this session)

Surveyed options:

1. **Drop the `events` table on the same connection immediately before calling the function under test** — `conn.execute("DROP TABLE events", []).unwrap()`. `record_github_grant`'s internal `append_event` call chains through `current_chain_head` (`audit.rs:1251-1272`), whose first statement is `conn.prepare("SELECT id, hash FROM events WHERE ...")` (`audit.rs:1255-1262`, read this session) — with `events` dropped, this `.prepare()` call fails immediately with a `rusqlite::Error` ("no such table: events"), which propagates via `?` out of `append_at_head`, out of `append_event`, out of `record_github_grant`, causing the enclosing `tx` (still holding the already-staged `session_grants` insert) to `Drop` without `.commit()` — and `Transaction`'s `Drop` impl defaults to `DropBehavior::Rollback` (`rusqlite-0.32.1/src/transaction.rs:127,242-246`, read this session), issuing a real `ROLLBACK`. **This session compiled and ran exactly this scenario** (`fixed_grant_rolls_back_session_grants_row_when_append_fails`, prototype file, deleted after use) and confirmed: `session_grants` row count == 0 after the forced failure, `has_github_grant` == false, and after repairing the schema via `conn.execute_batch(brokerd::audit::SCHEMA_DDL)` (the same `pub const SCHEMA_DDL` `open_audit_db` uses, `audit.rs:95` `"CREATE TABLE IF NOT EXISTS events ..."`, idempotent by construction) a retry succeeds with exactly one grant row and exactly one event. **Fast (sub-millisecond), fully deterministic, zero threads, zero timing assumptions, zero production-code changes.** This is the recommended **primary** approach.
2. **A second connection holding a competing write lock, forcing `SQLITE_BUSY` on the enclosing `BEGIN IMMEDIATE`.** `AUDIT_BUSY_TIMEOUT_MS` is a hardcoded `5000` (`audit.rs:81`, `const AUDIT_BUSY_TIMEOUT_MS: u64 = 5000;`, private, not `pub`, no env override) applied via `conn.busy_timeout(...)` in `open_audit_db` (`audit.rs:729`, read this session) — meaning a busy-lock test would need to hold a competing write lock for close to 5 seconds before the `BEGIN IMMEDIATE` itself gives up and returns `SQLITE_BUSY`. It also fails BEFORE the `session_grants` insert ever stages (the whole transaction can't start), so it does not exercise "fault strictly after the grant insert staged" — it exercises a different, earlier failure mode (can't even begin). Useful as a **secondary/fallback** oracle for D2-style lock contention, but slow (~5s) and not the right shape for CR-01's specific claim.
3. **A read-only DB file or revoked file permissions.** Same problem as (2) — `BEGIN IMMEDIATE` itself would fail to acquire the write lock, so nothing ever stages. Not recommended for CR-01's specific "insert staged, then append fails" claim.
4. **A `cfg(test)`/fixture seam inside `record_github_grant` itself** (e.g. an injectable failure point). Rejected — it would require modifying production code with test-only branching logic inside the TCB, which this codebase's conventions and the "no production code touched by the test" discipline (mirroring `audit_chain_fork_regression.rs`'s own approach — no seam, just real connections and real schema manipulation) both argue against.
5. **SQLite `PRAGMA`s** (e.g. `PRAGMA query_only=ON`). Considered but rejected: `query_only` blocks ALL writes including the initial `session_grants` insert, same problem as (2)/(3).

**Recommendation:** Primary = option 1 (drop `events`, repair via `SCHEMA_DDL`, retry). Fallback/secondary (optional, lower priority, and clearly slower) = option 2, only if the plan wants an additional lock-contention-specific oracle alongside the primary one; not required to satisfy success criterion 2, which asks specifically for "an append failure" + "a retry," both of which option 1 satisfies deterministically. `[VERIFIED: mechanism empirically proven this session via a compiled-and-executed throwaway test, since deleted; git status clean before and after]`

### Q4 — Retry semantics (exact `INSERT OR IGNORE` behaviour + what to assert)

`record_github_grant`'s existing (unfixed) shape (`audit.rs:542-566`, read this session): `let rows_affected = conn.execute("INSERT OR IGNORE INTO session_grants (session_id, grant_type, granted_at) VALUES (?1, ?2, ?3)", ...)?;` — the `session_id` column is the table's `PRIMARY KEY` (confirmed by the existing test `github_grant_record_is_idempotent`'s comment "no duplicate capability row (INSERT OR IGNORE via the session_id PRIMARY KEY)" and by `github_grant_migration_is_idempotent`'s and `created_pr_migration_is_idempotent`'s parallel idempotent-migration pattern), so `rows_affected == 1` iff this is the FIRST successful grant for that session; `rows_affected == 0` means either a genuine replay (already-committed row from an earlier success) or — pre-fix — a retry after a failed prior append (an orphaned row with no event). Post-fix, because the insert and the append share one transaction, `rows_affected == 0` can only mean a genuine replay (the row, if present, always has its event, by construction) — this is precisely what closes the CR-01 gap.

**What the regression should assert**, both after the forced failure and after the successful retry:

## Common Pitfalls

### Pitfall 1: Forgetting `record_github_grant`'s own doc comment describes the OLD two-phase shape
**What goes wrong:** The function's docstring (`audit.rs:513-536`, read this session) currently says "Two writes under the caller's connection: 1. ... 2. ..." describing exactly the pre-fix two-statement behavior CR-01 is fixing. If the fix lands without updating this comment, it becomes a fresh instance of the same AR-05/AR-06 comment-drift class the moment it's written.
**Why it happens:** The fix changes the mechanism (one transaction) but the docstring describes the old one (two separate writes).
**How to avoid:** Update the docstring alongside the code change to describe the new atomic-transaction shape, in the same commit.
**Warning signs:** Docstring still says "under the caller's connection" or enumerates "two writes" as separate/sequential rather than "one transaction."

### Pitfall 2: Testing the fault-injection path with a shared/reused connection across assertions
**What goes wrong:** After forcing the `events` table to be dropped and observing the rollback, a naive test might try to `query_row` against `events` before repairing the schema (e.g. to double check something), which throws "no such table" and aborts the test with a confusing panic rather than a clean assertion failure.
**Why it happens:** The `events` table is genuinely absent until `SCHEMA_DDL` is re-run.
**How to avoid:** Only query `session_grants` (a table that was never dropped) between the forced failure and the schema repair; query `events` only after `conn.execute_batch(SCHEMA_DDL)` has run.
**Warning signs:** A test panics with a `rusqlite::Error` message containing "no such table: events" instead of failing a normal `assert_eq!`.

### Pitfall 3: Assuming `Transaction::new_unchecked` needs no re-entrancy guard of its own
**What goes wrong:** If some future caller ever invoked `record_github_grant` from inside an already-open transaction on the SAME connection, `Transaction::new_unchecked`'s `"BEGIN IMMEDIATE"` would fail with a genuine SQLite "cannot start a transaction within a transaction" error (fail-closed — propagates as `Err`, not a silent no-op), unlike `append_event`, which has an explicit `is_autocommit()` branch to detect and join an enclosing transaction instead of nesting.
**Why it happens:** `record_github_grant` is currently called ONLY from bare, freshly-opened, autocommit connections (`main.rs:1255`, and every test call site) — never from within another function's already-open transaction — so this branch is currently unreachable, but it is not defended against structurally the way `append_event` itself is.
**How to avoid:** Keep `record_github_grant` called only from autocommit connections (matches every current call site); if a future phase needs to call it from within an enclosing transaction, it should gain the same `is_autocommit()` re-entrancy check `append_event` has, at that time — not preemptively required for CR-01's scope, but worth a one-line comment noting the current unconditional-open assumption.
**Warning signs:** A new call site passes a `&Transaction` (deref'd to `&Connection`) into `record_github_grant`.

### The fix (verified working this session — do not modify implementation now; this is the exact pattern to hand the planner)

```rust
// Proposed replacement for crates/brokerd/src/audit.rs:537-567 (record_github_grant).
// Empirically compiled and run this session as a throwaway prototype (deleted after use).
pub fn record_github_grant(
    conn: &rusqlite::Connection,
    key: &[u8],
    session_id: &str,
) -> Result<()> {
    let tx = rusqlite::Transaction::new_unchecked(
        conn,
        rusqlite::TransactionBehavior::Immediate,
    )?;

    let rows_affected = tx.execute(
        "INSERT OR IGNORE INTO session_grants (session_id, grant_type, granted_at) \
         VALUES (?1, ?2, ?3)",
        rusqlite::params![session_id, "github.pr", chrono::Utc::now().to_rfc3339()],
    )?;

    // Replay-suppression: only emit the authorize event on a FRESH grant.
    if rows_affected == 1 {
        let session_uuid = uuid::Uuid::parse_str(session_id)?;
        let (parent_id, parent_hash) = match current_chain_head(&tx, session_id)? {
            Some((id, hash)) => (Some(id), Some(hash)),
            None => (None, None),
        };
        let event = Event::new(
            uuid::Uuid::new_v4(),
            parent_id,
            session_uuid,
            format!("grant:github.pr:{session_id}"),
            "github_grant_authorized".to_string(),
            chrono::Utc::now(),
            vec![],
        );
        // append_event detects the enclosing transaction (tx.is_autocommit()
        // == false) and appends at the locked durable head WITHOUT opening a
        // nested transaction — the same choke point every other production
        // append site goes through.
        append_event(&tx, key, &event, parent_hash.as_deref())?;
    }
    tx.commit()?;
    Ok(())
}
```

```rust
    assert!(has_github_grant(&conn, &session_id));
    assert!(verify_chain(&conn, &session_id, TEST_KEY));
}
```
